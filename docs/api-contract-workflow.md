# Application API contract workflow

Nemeo has two related TypeSpec layers:

1. `docs/event-model/models/<system>/contracts/` is generated by `em api generate` and defines
   public Event Model commands, events, views, and their schemas.
2. `typespec/systems/<system>.tsp` defines the HTTP binding for that system: routes, transport
   projections, authentication, errors, pagination, and MCP metadata.

`typespec/main.tsp` only assembles the system bindings and shared contract definitions.

The generated OpenAPI artifact is published at the repository root as `open-api.yaml` for client
generators and external tooling.

Every application operation must document its mapping to the Event Model system, slice, and public
command/view. Reuse generated domain shapes when transport semantics match. Define a named request
or response projection when HTTP concerns differ, and explain the difference in the binding.

Do not inherit a generated command or view interface when that would publish unrelated domain
operations or expose a domain operation with the wrong HTTP shape. Use a named binding interface
with explicit operation mappings in that case; the generated contract remains the source for the
domain types and the binding remains the source for transport semantics.

The application binding must not expose every generated event or view automatically. It is the
explicit boundary between the domain contract and HTTP/OpenAPI.

Validate both layers together:

```bash
em api check docs/event-model/models/<system>/<system>.em
npm run contracts:check
```
