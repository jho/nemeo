# Nemeo agent guidance

## Architecture decision changes

When working on an architecture decision issue:

1. Read the issue, relevant product decisions, the Event Model, and existing ADRs first.
2. Do not create an ADR for an unresolved or merely proposed decision.
3. When the decision is accepted, update the ADR with the decision, rationale, alternatives, and
   consequences.
4. In the same change, update `.specify/memory/constitution.md` with the concise normative constraint
   that planning agents and implementation workflows must enforce.
5. In the same change, update `docs/architecture/decisions.md` so the issue and ADR status are
   discoverable.
6. Link the ADR from the constitution and link the issue from the ADR.
7. Run the SDD and repository validation checks before opening the PR.

The ADR is the record of what and why. The constitution is the enforcement-facing record of how
future work must comply. Do not copy the full ADR into the constitution, and do not silently resolve
an open product decision as an architecture constraint.

## Event Model boundaries

Nemeo's bounded-context boundaries are `iam`, `feeds`, `ledger`, and `budgeting`.

- `iam` owns authentication identity, profiles, household membership, invitations, and access.
- `feeds` owns external provider connections, synchronization, retries, normalization, and provider
  observations; it does not own canonical accounts or transactions.
- `ledger` owns canonical accounts and transactions, including categorization and transfer
  associations.
- `budgeting` owns budgets, categories, targets, and budget decisions; pace and reporting are
  derived views unless a later decision establishes a durable domain fact.

Use these initial aggregate lanes when modeling: `User` and `Household` (IAM), `Connection` and
`SyncRun` (Feeds), `Account`, `Transaction`, and `Rule` (Ledger), and `Budget` and `Category`
(Budgeting). A lane requires its own consistency boundary and state lifecycle; do not create one for
every feature, projection, or automation. `Rule` is an internal learned-preference boundary for
category assignment and transfer linkage, not a generic MVP rule-management product. `Transfer`,
`Categorization`, `Target`, `Pace`, `Progress`, and `Dashboard` are not aggregates.

When the model is decomposed into multiple `em` models, keep one model directory per context under
the shared system manifest. Cross-context behavior must use published events, views, commands, or
translations. Do not invent aggregate lanes from feature names, and do not share persistence between
contexts. See [ADR 0022](docs/architecture/adrs/0022-bounded-context-model-and-provider-feed-boundary.md).

Each context model MUST have a checked-in SVG generated by `scripts/render-event-models.sh`. Do not
edit rendered SVGs by hand; regenerate them whenever a model changes. CI checks that the committed
diagrams match their `.em` sources.

## Feature implementation

Start from a ratified Event Model slice in a short-lived feature batch. `em` is authoritative for
the model and slice lifecycle. For Nemeo, exporting a documented slice into the implementation
backlog is its ratification boundary; the slice must have `status: ready-to-implement`,
`ratifiedBy`, and `ratifiedOn` before planning. Each implementation PR names its model and slice
key. Dependent PRs may form a stack whose design layer is not merged separately; the complete batch
merges once. Record post-merge implementation state with `em` commands and follow
[`docs/event-modeling/workflow.md`](docs/event-modeling/workflow.md) for artifact ownership and
phase gates.

## Feature code layout

Business-capability slices belong under `src/features/<aggregate-or-context>/<slice>/`, following
the Event Model's aggregate/consistency context. A slice owns its application capability,
command/query handlers, domain rules, ports, and slice-specific tests. Do not invent a larger
bounded-context hierarchy until the model has an independent language, contract, ownership, or
deployment boundary that requires one.
Transport registration belongs under `src/interfaces/`; replaceable adapters belong under
`src/infrastructure/`; cross-cutting support such as telemetry belongs in its own supporting module.
Interface and cross-feature code may use only a feature's explicit public capability and must not
import another feature's internal handlers, domain objects, or persistence code. Preserve the
Event Model slice boundary even when a feature is relational rather than event-sourced.

## Contract workflow

Nemeo has two related contract layers. Agents MUST keep their ownership distinct:

1. Event Model domain contracts are generated from public Event Model elements with `em api
   generate`. Generated files live beside their model under the model's `contracts/` directory,
   are checked with `em api check`, and MUST NOT be hand-edited.
2. Application API contracts are authored in TypeSpec under `contracts/api/`. They define the
   versioned HTTP resources and business commands consumed by the web client and exposed to MCP.
   OpenAPI, client types, documentation, and MCP bindings are generated outputs; they MUST NOT be
   parallel hand-authored sources of truth.

When designing a slice, the designer MUST identify its application API operations, operation IDs,
request and response models, errors, authorization scope, and whether an operation is MCP-exposed.
Each operation MUST map to the slice or to an explicitly documented cross-slice query. Implementers
MUST consume the approved contract and MUST NOT invent routes or payloads in transport code.

Before implementation, run the repository's contract generation and validation checks together with
the Event Model checks. Generated artifacts are reproducible outputs and are never edited to fix a
runtime or business-rule problem; change the TypeSpec or Event Model source instead.

Each context model MUST have a checked-in SVG generated by
`scripts/render-event-models.sh`. Do not edit rendered SVGs by hand; regenerate them whenever a
model changes. CI checks that the committed diagrams match their `.em` sources.

system manifest. Cross-context behavior must use published events, views, commands, or translations.
Do not share persistence between contexts. See

## UI design artifacts

Use [`docs/design/README.md`](docs/design/README.md) for UI artifact locations and conventions.

- Keep the root dashboard prototype as the central MVP information-architecture reference until
  its existing ADR links are intentionally migrated.
- Put new slice-level wireframes in `docs/design/wireframes/` and broader interactive prototypes
  in `docs/design/prototypes/`.
- Link a UI artifact from the corresponding slice document and include its route, visible data,
  action/next step, and relevant loading, empty, error, and permission states.
- Use the accepted UI design system and navigation ADRs. Do not invent reusable components or
  interaction patterns silently.
- Treat wireframes and prototypes as presentation design, not as replacements for the PRD, ADRs,
  Event Model, slice scenarios, or API contracts.
- Do not create wireframes for headless/API-only slices; document the caller-facing interaction
  contract instead.
